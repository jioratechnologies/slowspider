SLOW SPIDER — Workspace, Task & Note Collaboration Platform

Commercial & Technical Proposal

This proposal covers design, development, deployment, user training, technical documentation, and post-implementation warranty support for Slow Spider — a multi-platform workspace organizer with live collaboration across web and Android clients.

1. Product Perspective

Slow Spider is a workspace-based productivity platform: teams organize work as Categories, Clusters, and Tasks on a shared board, attach rich Notes to any item, and see each other's changes live. It is delivered as three coordinated surfaces — a web application, an Android application, and a backend API — all speaking to one shared source of truth, so a change made on one device is reflected on every other device without a manual refresh.

The platform is architected client-agnostic from day one: every client talks to a single API gateway over REST and WebSocket, never to the database or messaging layer directly. This keeps the system open to future clients — an iOS app, a browser extension, a desktop app — as additional consumers of the same gateway, with no backend rework.

3. System Architecture

All client traffic — REST requests and the live-update connection alike — passes through a single API gateway. The backend is the only component that ever talks to the database, cache, or event bus; no client connects to them directly.

  • API Gateway — single entry point for every client, REST and WebSocket alike; declarative configuration, centralized rate limiting and CORS.
  • Backend Service — owns all business logic and is the only component with credentials to the database, cache, storage, and event bus. Terminates each client's live-update connection and relays events through, rather than exposing internal infrastructure directly.
  • Event Bus — internal publish/subscribe backbone for live sync (task, cluster, note, workspace changes), with durable delivery so a briefly-disconnected client catches up instead of missing updates.
  • Shared contracts — request/response shapes defined once and consumed by both backend and web, so the two never drift apart.

4. Technical Requirements

Web Client

Next.js (React), server-rendered UI, calls the backend exclusively through the gateway.

Android Client

Flutter (Dart), single codebase, Material-based UI, live-sync client built in.

Backend Service

Node.js (NestJS), REST + WebSocket, containerized.

API Gateway

Declarative, DB-less gateway in front of the backend — routing, rate limiting, CORS.

Database

PostgreSQL (managed), relational schema for workspaces, boards, tasks, notes.

Cache

Managed Redis — session/rate-limit and short-lived state.

Event Bus

Internal pub/sub with durable (replayable) delivery for realtime sync.

Object Storage

S3-compatible storage for note attachments (images, video, voice, files), quota-enforced per user.

Authentication

Bearer-token session auth, verified on every request; workspace-membership checked per resource.

Containerization

Docker Compose for backend, gateway, and event bus — one deploy artifact per environment.

Concurrent Editing

Conflict-free merge (CRDT) for simultaneously edited note text.

Environments

Separate staging and production configurations, gateway routes identical across both.
